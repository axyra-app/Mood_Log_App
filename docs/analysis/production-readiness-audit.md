## Bloqueos

1. **Privacidad y regulación:** los textos de Términos/Privacidad/consentimiento siguen como borradores. Ánimo, diario y pulso pueden revelar datos sensibles. Se requiere revisión jurídica colombiana de finalidades, autorización previa/expresa/facultativa, derechos, retención, contratos/transferencias y obligaciones del responsable; además, concepto regulatorio escrito sobre el uso previsto y claims frente a INVIMA. No activar uso real de estas funciones antes de completar esa puerta.
2. **Entorno y derechos:** la revisión solo demuestra controles locales. No se consultaron proyectos Firebase/Vercel/Groq ni el bucket, reglas, regiones, App Check, retención, ZDR/contratos, logging, límites organizacionales o borrado en proveedores. Falta staging aislado, recorrido integrado desde navegador y prueba de exportación/supresión con fallos parciales. Al habilitar borrado, configura `FIREBASE_STORAGE_BUCKET` con el bucket exacto de `VITE_FIREBASE_STORAGE_BUCKET`; la API verifica que coincidan en runtime y falla de forma cerrada si falta alguno o divergen.
3. **Wear OS:** el build debug ya compila, pero el APK no se ha instalado ni probado en emulador/reloj. El build emitió un aviso no fatal de SDK XML v4 frente a una herramienta que entiende hasta v3, además de advertencias de Gradle; alinear y revisar el toolchain antes de release. El chequeo de compilación no sustituye una prueba de sensor, backups ni compatibilidad física.
4. **Entrega:** los cambios revisados siguen locales y sin commit. La última ejecución remota de CI observada es del 17 de octubre de 2026 sobre el commit base `0bad35a`; no valida este checkout ni su paso de Wear OS. La CI de GitHub debe ejecutarse con el cambio final antes de un release.

## Evidencia local revisada

- `frontend/package.json`, API, reglas Firestore/Storage, workflows y documentación de despliegue.
- Actualización posterior a la medición base: la API conserva el límite por UID y suma un contador transaccional compartido configurable por scope Firestore (RPM y ventana móvil de 24 h); Vercel falla de forma cerrada si no se configura. Esto aún no está conectado a límites del proyecto/organización Groq, no aplica a otras bases/servicios, y un único documento puede ser cuello de botella; valores y rendimiento de staging pendientes.
- Endurecimiento posterior: la función de borrado ya no adivina el bucket Storage por el ID del proyecto ni usa el proyecto demo como fallback. Exige `FIREBASE_PROJECT_ID` y que `FIREBASE_STORAGE_BUCKET` coincida exactamente con `VITE_FIREBASE_STORAGE_BUCKET` antes de inicializar Admin/Storage. No se ha verificado la configuración de Vercel ni el borrado del bucket remoto.
- En la revisión del 20-11-2026 se retiró del código activo el detector heurístico de crisis no conectado, el tipo de reporte `crisis_assessment` y el default inerte `crisisAlerts`; las referencias en borrado se mantienen para cubrir colecciones heredadas. Esto reduce la posibilidad de presentar una heurística no validada como función de emergencia, pero no crea capacidad de detección o respuesta.
- Revisión posterior de gates (20-11-2026): aceptación legal y autorización sensible vuelven a leer perfil/estado de eliminación dentro de la transacción; la autorización sensible comprueba además el evento legal vigente y la solicitud de IA valida consentimiento vigente antes de crear su evento/lease. Repetir la misma decisión vigente de términos o consentimiento sensible es ahora una operación sin escrituras adicionales. Es código local sin suite/typecheck posteriores; requiere casos de concurrencia e idempotencia en Firestore Emulator y no se considera evidencia de producción.
- Decisión posterior de persistencia: para la siguiente etapa longitudinal se escogió solo almacenamiento privado local en el reloj, sin teléfono ni nube. Retención, cifrado, exportación, borrado y consentimiento específico continúan pendientes. La documentación oficial de Wear OS indica que el Data Layer `DataItem` puede respaldarse en nube; no usarlo para biometría bajo una promesa “sin nube” sin una evaluación explícita.
- La eliminación de cuenta ahora usa `recursiveDelete` para cada documento raíz propio en las colecciones listadas, además del borrado recursivo de perfil/ajustes. Un fixture simula una subcolección bajo un registro de diario y más de 400 documentos heredados; la suite API pasó 58/58 y typecheck pasó. Esto no prueba permisos ni comportamiento de `recursiveDelete` contra Firestore Emulator o un proyecto real.
- La exportación local v8 se trasladó a `/api/user-data-export`: valida token con revocación, deriva el UID de la sesión, transmite NDJSON e incluye subcolecciones y colecciones heredadas declaradas. La suite API verifica aislamiento por UID, registros anidados, proyección de `aiUsage` y conflicto ante borrado pendiente. Permanecen fuera binarios de Storage, decisiones locales de Wear OS y logs externos; falta probar tamaño, duración y desconexiones en staging.
- La allowlist de colecciones exportables y borrables ahora vive en un único módulo compartido; una prueba API comprueba que todas las colecciones activas/heredadas definidas pertenezcan a ese inventario para reducir omisiones por deriva. El test no descubre colecciones remotas ni reemplaza el cotejo en staging.
- El prototipo Wear OS ahora excluye explícitamente SharedPreferences/archivos/bases privadas de backup cloud y transferencia directa, con reglas heredadas para Android 11 o menor. Android advierte que `allowBackup="false"` por sí solo puede no impedir transferencias directas en algunos fabricantes; una prueba de configuración y el parseo XML local pasan, pero aún falta `:app:assembleDebug` y probarlo en reloj.
- En una ejecución anterior al endurecimiento reciente: reglas 29/29, API 58/58, configuración 10/10, unidades 14/14; typecheck, build y verificación PWA pasaron. Estos resultados no cubren el código cambiado posteriormente en esta continuación. La suite automatizada tampoco sustituye recorridos UI/staging.
- Wear OS: siete comprobaciones Java puras pasaron en una ejecución anterior, incluyendo selección de lectura y permisos API 35/36. En esta continuación `:app:assembleDebug` también pasó y generó un APK; la lectura de sensor, el permiso real, backups y la instalación en reloj siguen sin validación.
